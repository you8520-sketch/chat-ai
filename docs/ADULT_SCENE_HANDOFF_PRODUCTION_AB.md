# Adult scene handoff — production-equivalent revalidation

Date: 2026-07-30  
Branch: `codex/adult-scene-model-handoff`  
Main merge: not performed  
Production flag: not enabled  
Final verdict: **NOT MERGEABLE — production gate failed before the 40-call run**

## Why the previous 252.2 / 555.6 prompt-token result was small

The previous script was a micro-fixture prompt-continuity test:

- it used a short test-only `COMMON_SYSTEM`
- A used `slice(-4)`, which meant four messages/two exchanges
- B used `slice(-6)`, which meant six messages/three exchanges
- it did not call `buildContext()`
- its historical assistant responses were much shorter than production
- both A and B were generated by Gemini, not DeepSeek

The old A/B numbers and approximately 11.52/12.59 KRW cost estimates remain in
the historical report, but are now labeled **micro-fixture only**.

## New harness

`scripts/adult-scene-handoff-production-ab.ts`:

- calls the real `buildContext()`
- uses real character/world, persona, user note, Muse/prose, Speech Lock,
  archive/summary, long-term memory, episodic recall, status/trigger, lorebook,
  recent RAW, current-user-input, continuity-packet, and continuation paths
- uses the production `buildOpenRouterRequestBody()` and production response
  target (`targetResponseChars=3200`)
- opens no app database
- performs no message write, point deduction, or route-state mutation
- prepares the final pre-handoff assistant turn with the assigned real
  Gemini 3.6 Flash or GPT-5.6 Luna model
- validates every historical assistant fixture at 2,000–4,000 characters
- hard-checks complete exchange/message counts
- checkpoints provider usage and output character metrics
- refuses to spend the 40-call gate when the RAW gate fails

The fixture contains ten required scene types and alternates the origin model
between Gemini and Luna. Ten real origin responses were generated. Provider
outputs outside the historical 2,000–4,000-character distribution were retried
when short; long output fixture copies preserve the actual prefix and cap at
4,000 characters.

## Dry-run RAW result

A correctly retained four complete exchanges/eight messages in all ten scenes.

B targeted up to six complete exchanges/twelve messages under a 10,000-token
RAW budget. With 2,000–4,000-character assistant responses it normally retained
only four exchanges. In `tension_to_explicit_dialogue`, B retained only three
exchanges/six messages while A retained four/eight.

This is a gate failure:

```text
tension_to_explicit_dialogue:
A = 4 exchanges / 8 messages
B = 3 exchanges / 6 messages
```

Cause: A forces `minimumTurns=4` and may exceed the budget, while B uses
`minimumTurns=2` and stops at the budget. Therefore the supposed expanded B arm
can carry less RAW than A for production-length outputs.

The 40-call test was intentionally not run because it would compare a
continuity packet plus less RAW against a forced four-exchange baseline. That
would not answer whether six-exchange handoff improves continuity.

## Prompt-token breakdown and estimator error

The harness records:

```ts
{
  totalPromptTokens,
  systemAndMasterPromptTokens,
  characterAndWorldTokens,
  museAndSpeechLockTokens,
  memoryAndSummaryTokens,
  statusAndTriggerTokens,
  rawHistoryTokens,
  sceneContinuityPacketTokens,
  currentUserInputTokens,
  tokenBreakdownError
}
```

Provider `usage.prompt_tokens` is the total source of truth. Component values
are estimated with the same repository estimator and proportionally scaled to
the provider total. The unscaled estimator error in the two probes was:

- A: `14,881 - 17,537 = -2,656` tokens (-17.8% of provider total)
- B: `15,321 - 18,318 = -2,997` tokens (-19.6% of provider total)

The component estimator itself therefore also misses the requested ±15%
tolerance and needs calibration before component costs are treated as exact.

Provider-scaled component attribution:

## Comparison with a recent production receipt

The recent production request supplied during the earlier diagnosis recorded
29,542 main-RP input tokens. Against that reference:

- A probe: 14,881, which is 49.6% lower
- B probe: 15,321, which is 48.1% lower

The new fixture is much closer than the old 252/556-token micro fixture, but it
still does not meet the ±15% production-equivalence criterion. The main
remaining difference is the much larger real character/canon payload in the
production chat.

## Output-length result

The two DeepSeek probes both reached the 2,000–4,000-character target. This is
2/2, not the required 90% of 40 outputs, so it is only a transport/length probe
and not a pass for the final length gate.

The old 11.52/12.59 KRW micro-fixture figures must not be used.

## Final gate decision

Failed:

1. B can retain fewer exchanges than A at production response lengths.
2. Probe prompt tokens are outside ±15% of the available production receipt.
3. Only 2 DeepSeek probe calls were run; the required 40-call gate was blocked.
4. Blind A/B means and standard deviations cannot be calculated.
5. A 90% production-length success rate cannot be established from two calls.

Passed:

1. The new payload uses the actual `buildContext()` path.
2. A means four exchanges/eight messages.
3. Complete exchange/message counts are recorded and asserted.
4. Real Gemini/Luna origin outputs were prepared.
5. Both probe arms ended at DeepSeek V4 Pro.
6. Provider usage, finish reason, output characters, Korean characters,
   paragraphs, latency, and cache reads are recorded.
7. App DB writes, user point deduction, and route-state mutation are absent.

**Do not merge this branch and do not enable `ADULT_SCENE_ROUTING_ENABLED`.**

## Required next decision

Before the 40-call gate can be valid, choose and implement one consistent RAW
contract:

- make both A and B obey the same budget-floor policy while guaranteeing
  B never retains fewer exchanges than A, or
- define B as a token-budget expansion rather than a six-exchange expansion,
  and update the hypothesis/report accordingly.

Then build fixtures from a sanitized copy of the actual large production
character/canon payload so provider prompt tokens fall within ±15% of recent
production receipts. Only after those two dry gates pass should the 40-call
blind A/B run begin.
